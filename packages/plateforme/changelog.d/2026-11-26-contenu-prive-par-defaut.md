### Assistants
- `write` creating outside a team folder or your private space puts the content in your private space, unless it passes `space: "everyone"`; the answer says the space.
- Moving or renaming a content keeps its space, written on it: a private content stays private; a team's or everyone's content takes the access rules of its new folders.

### Hosts
- Migrations: apply `20261126172651_platform_espace_ecrit.sql` together with the package (development file, merged into the version's single file before the tag): every node gets the owner it inherited, written on it (no visibility changes, `updated_at` kept), `owner_kind` becomes required, a node created without owner takes its parent's, and under a session only its parent's or its author's own. The package without it reads an inherited owner as none; the migration without the package writes every new assistant page in the shared space as before, but private pages moved under a shared folder stay private. Two package versions on one database (canary and production) cannot run around it: the previous package on a migrated database fails `admin_node transfer_owner` with `inherit` (`23514`), this package on a database not yet migrated refuses every write that falls into a private space by default (`42501`). Apply the migration, then deploy this package to every host reading that database at once; until then, do not transfer with `inherit`. The backfill rewrites every node without owner in one transaction that blocks writes on `nodes`: plan it outside working hours on a large database.
- Schemas: `writeNodeSchema` takes `space` (`"everyone"` or `"private"`), for a creation only.
- UI: « Partager · <espace> » of a node names the space written on it (its owner), no longer the section of its path.
- Server: `transferOwner` writes the new owner on the node and on the descendants that share its space; `inherit` writes its parent's.
