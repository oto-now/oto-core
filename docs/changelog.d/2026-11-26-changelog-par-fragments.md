## [2026-11-26] — Méthode : un fichier par entrée de journal, pour que les pull requests ne soient plus en conflit
**Quoi :** une pull request n'écrit plus dans `docs/changelog.md`, figé, ni sous `## Unreleased` de `packages/plateforme/CHANGELOG.md`. Elle ajoute un fichier neuf : `docs/changelog.d/AAAA-MM-JJ-<sujet>.md` pour son entrée (format inchangé, lu par nom de fichier décroissant, exclu de l'arbre de code comme `docs/changelog.md`), et, si elle change ce que voit un hôte ou un assistant, `packages/plateforme/changelog.d/AAAA-MM-JJ-<sujet>.md` pour ses lignes `### Assistants` et `### Hosts`. La pull request de version les verse dans la section de la version par `pnpm changelog:version <x.y.z>` (`scripts/changelog-version.mjs`, qui verse aussi les lignes encore écrites sous `## Unreleased`, puis supprime les fragments) ; `scripts/ci/version-publiable.mjs`, joué par `ci.yml` et `publish.yml`, refuse une version où un fragment ou une ligne sous `## Unreleased` reste. Les fragments ne partent pas dans le paquet publié (`files` de son manifeste). Un fragment du paquet se nomme comme une entrée du dépôt, `AAAA-MM-JJ-<sujet>.md`, et se verse par ordre de date. Tests : `docs/changelog.md` figé (aucune entrée datée après le 2026-11-26) et format d'une entrée de `docs/changelog.d/` (`changelog-entrees`), format d'un fragment du paquet et versement (`changelog-version`, `package-publish`), fragment restant refusé au tag (`version-publiable`), entrée écrite après les checks hors de l'arbre de code (`arbre-de-code`, `commit-depuis-export`, `recu-ci`).
**Pourquoi :** chaque fusion remettait toutes les pull requests ouvertes en conflit sur le journal, et chaque recalage coûtait une vérification complète ; un fichier neuf par changement n'entre en conflit avec aucun autre.
